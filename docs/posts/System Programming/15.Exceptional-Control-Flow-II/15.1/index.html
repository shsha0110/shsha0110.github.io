[System Programming] 15. Exceptional Control Flow II

시그널을 ’전달(받는 쪽 PCB의 비트 켜기)’과 ’수신(사용자 모드로 돌아가기 직전의 동작 실행)’이 분리된 소프트웨어 수준의 예외적 제어 흐름으로 이해하고, kill · sigaction · sigprocmask · sigpending과 프로세스 그룹을 거쳐, 합쳐져 사라지는 SIGCHLD, EINTR로 끊기는 시스템 호출, 핸들러와 메인 사이의 경쟁 조건, 안전한 핸들러 작성 지침까지 예제 출력으로 따라갑니다.

“시그널은 커널이 프로세스에게 ’어떤 종류의 사건이 일어났다’는 사실 하나만 알리는 소프트웨어 수준의 예외적 제어 흐름이며, 전달(받는 쪽 PCB의 비트 하나를 켜기)과 수신(그 프로세스로 돌아가기 직전에 비트를 보고 동작을 실행하기)이 분리되어 있다는 데서 그 성질과 함정이 모두 나옵니다.”

시그널마다 종료 · 무시 · 정지 · 계속 중 하나의 기본 동작이 정해져 있고, 프로세스는 sigaction으로 핸들러를 등록해 시그널을 잡거나, sigprocmask로 차단하거나, 무시할 수 있습니다(SIGKILL과 SIGSTOP은 예외). 커널은 시그널을 전달할 때 받는 프로세스의 PCB에 대기 중(pending) 표시를 해 두었다가, 그 프로세스로 돌아가기 직전에 대기 중이면서 차단되지 않은 시그널을 골라 동작을 실행합니다. 대기 표시가 종류마다 비트 하나뿐이므로 시그널은 큐에 쌓이지 않고, 그래서 SIGCHLD 핸들러는 waitpid(-1, …, WNOHANG)을 반복해 끝난 자식을 모두 수확해야 합니다. 핸들러는 메인 프로그램과 동시에 실행되는 별개의 논리적 흐름이어서 시스템 호출을 끊어 EINTR을 일으키고(재시도 루프나 SA_RESTART로 해결), 전역 변수를 두고 경쟁 조건을 만듭니다. 그래서 핸들러는 단순하게 짜고, 비동기 시그널 안전 함수만 부르고, errno를 보존하고, 공유 자료를 건드리는 동안 시그널을 차단하고, 플래그는 volatile sig_atomic_t로 선언해야 합니다.

2. 고수준 메커니즘: 시그널 개요 (High-level Mechanisms: Signal Overview)

2.1 시그널이란 무엇인가 (Signals)

Note정의 (Signal)

시그널(signal)은 시스템에서 어떤 종류의 사건(event)이 일어났음을 프로세스에게 알리는 메커니즘입니다.

  • 예외적 제어 흐름의 고수준 형태입니다. 14강의 예외 · 인터럽트와 비슷하지만 하드웨어가 아니라 소프트웨어 수준에서 일어납니다. 인터럽트가 사건을 커널에 알린다면, 시그널은 사건을 사용자 프로세스에 알립니다.
  • 시그널의 종류는 작은 정수 하나로 나타냅니다.
    • 대부분의 시스템에서 1–31번입니다(man 7 signal 참조). 리눅스에는 이와 별도로 실시간 시그널(SIGRTMIN–SIGRTMAX)이 있지만, 이 강의가 다루는 것은 1–31번의 표준 시그널입니다.
    • 시그널이 전하는 정보는 그 종류와, 도착했다는 사실뿐입니다. 특히 같은 종류가 몇 번 왔는지는 남지 않습니다. 이 성질이 3.3절의 “시그널은 큐에 쌓이지 않는다”와 5장의 첫 번째 문제로 이어집니다.

시그널마다 서로 다른 사건이 대응합니다. 슬라이드의 표는 다음과 같습니다.

번호 이름 기본 동작 사건

  • 코어 덤프(core dump)는 종료 순간 프로세스의 메모리 이미지를 파일로 남겨, 나중에 디버거로 죽은 원인을 살펴볼 수 있게 하는 것입니다.

  • SIGCONT의 “무시”는 실행 중인 프로세스에는 (대기 중인 정지 시그널을 지우는 것 말고는) 아무 영향이 없다는 뜻입니다. 정지된 프로세스는 이 시그널이 보내지는 순간(이 강의의 전달) 커널이 다시 실행시키며, SIGCONT를 차단하거나 무시하고 있어도 마찬가지입니다.

3. 시그널의 개념 (Signal Concepts)

3.1 시그널 처리 방식 (Signal Handling)

커널은 시그널마다 받는 프로세스가 취할 기본 동작(default action)을 정해 둡니다.

기본 동작 커널이 하는 일
종료 / 코어(terminate / core) 프로세스를 끝냅니다(코어 덤프를 남기기도 합니다)
무시(ignore) 시그널을 조용히 버립니다
정지 / 계속(stop / continue) 프로세스를 멈추거나 다시 실행합니다

프로세스는 시그널에 어떻게 반응할지를 프로그램으로 정할 수 있습니다.

반응 의미 설정 수단(4장)
잡기(catching) 사용자가 정의한 시그널 핸들러(signal handler)를 실행합니다 sigaction, signal
차단(blocking) 차단을 풀 때까지 시그널의 수신을 미룹니다 sigprocmask
무시(ignoring) 시그널을 버립니다 핸들러 자리에 SIG_IGN
기본 동작 위 표의 동작을 따릅니다 핸들러 자리에 SIG_DFL
  • 앞 절대로 SIGKILL과 SIGSTOP은 잡기 · 차단 · 무시가 모두 불가능하고, 언제나 기본 동작을 따릅니다.
  • 차단과 무시는 다릅니다. 무시한 시그널은 버려지지만, 차단한 시그널은 사라지지 않습니다. 차단된 동안 도착한 시그널은 대기 중(pending)으로 남아 있다가, 차단을 푸는 순간 수신됩니다. “지금은 받지 않겠다”(차단)와 “앞으로도 받지 않겠다”(무시)의 차이이며, 4.12절의 block.c 출력에서 그대로 확인할 수 있습니다.

3.2 시그널의 출처 (Signal Sources)

시그널은 커널이 만들거나, 프로그램의 요청으로 만들어집니다.

  • 커널 안에서 일어난 사건의 결과로. 예를 들어 잘못된 메모리 접근은 다음 순서로 시그널이 됩니다.
    1. 프로세스가 잘못된 메모리 주소에 접근합니다.
    2. MMU가 저수준 예외인 #PF(페이지 폴트)를 일으킵니다.
    3. 커널의 예외 핸들러가 프로세스에 SIGSEGV(세그멘테이션 폴트)를 보냅니다.
  • 프로그램이 요청해서. 시스템 호출 int kill(pid_t, int sig)를 씁니다(4.5절).
    • 보내는 프로세스는 받는 프로세스와 사용자 ID가 같거나 특권(privileged)을 가져야 합니다. 다른 사용자의 프로세스를 마음대로 죽일 수 없게 하는 장치입니다.
  • 터미널에서.
    • 키보드: Ctrl-C, Ctrl-Z(4.4절)
    • /bin/kill, /usr/bin/killall: 임의의 시그널을 보내는 프로그램(4.2절)

첫 번째 경로는 두 수준의 ECF가 어떻게 이어지는지 보여 줍니다. 14강의 저수준 예외(페이지 폴트)를 커널이 먼저 처리하고, 그 결과를 고수준 ECF인 시그널로 바꾸어 사용자 프로세스에게 알립니다. 잘못된 포인터를 따라간 프로그램이 “Segmentation fault”를 남기고 죽는 것은 SIGSEGV의 기본 동작이 종료이기 때문입니다.

3.3 시그널의 전달과 수신 (Signal Delivery and Reception)

이 강의는 시그널이 프로세스에 닿는 과정을 두 단계로 나누어 부릅니다.

Note정의 (Signal Delivery, Pending Signal, Signal Reception)
  • 전달(delivery): 커널이 받는 프로세스의 PCB(process control block) 안에 있는 시그널 상태를 갱신하는 것입니다.
  • 대기 중인 시그널(pending signal): 전달되었지만 아직 수신되지 않은 시그널입니다. 한 종류당 대기 중인 시그널은 최대 하나입니다. 다시 말해 시그널은 큐에 쌓이지 않습니다(signals are not queued).
  • 수신(reception): 나중에 커널이 그 시그널 상태를 확인하고 선택된 동작을 실행하는 것입니다.
  • 슬라이드는 이 정의 아래에 “수신은 전달과 비동기다(Signal reception is asynchronous to delivery!)”라고 강조합니다. 전달은 시그널이 생기는 순간(kill 호출, 커널의 예외 처리, 터미널 입력 등)에 일어나지만, 수신은 받는 쪽이 다시 실행될 때까지 미뤄집니다. 그 사이에 무슨 일이 일어날지는 스케줄러에 달려 있습니다.
  • “최대 하나”는 대기 중인 시그널이 종류마다 켜고 끄는 표시 하나로 기록되기 때문입니다(3.7절). 같은 종류의 시그널이 수신되기 전에 두 번 전달되면 두 번째는 이미 켜진 표시를 다시 켤 뿐이므로 흔적이 남지 않습니다.
Warning용어 주의: 이 강의가 정의한 “전달”은 man 페이지의 “전달”이 아닙니다

같은 영어 단어가 자료마다 다른 단계를 가리킵니다. man 페이지를 읽을 때 특히 헷갈리기 쉽습니다.

단계 이 강의 교재(CS:APP) POSIX · man 페이지
PCB의 상태를 갱신 전달(deliver) 보냄(send, deliver) 생성(generate)
그 사이 대기 중(pending) 대기 중(pending) 대기 중(pending)
동작을 실행 수신(receive) 받음(receive) 전달(deliver)

man 7 signal이 “차단된 시그널은 차단이 풀릴 때까지 전달되지 않는다”고 쓸 때의 “전달”은 이 강의의 수신입니다.

슬라이드도 이 단어를 한 가지 뜻으로만 쓰지는 않습니다. 3.1절의 차단 설명(block delivery until the signal is later unblocked)은 man 페이지와 같은 뜻이어서 이 포스트에서는 “수신을 미룬다”로 옮겼고, 6장의 비교 슬라이드는 delivery를 두 단계 전체를 가리키는 말로 씁니다. 이 포스트의 “전달”과 “수신”은 위 정의를 따릅니다.

3.4 수신은 전달과 비동기다 (Signal Delivery and Reception)

앞 절의 정의를 시간 축 위에 놓으면 다음과 같습니다. 슬라이드는 핵심을 한 줄로 적습니다 — 시그널은 받는 프로세스가 문맥 교환에서 돌아가기 직전에 처리됩니다(immediately before returning from a context switch).

띠 실행 주체 일어나는 일
user code A A가 kill(B, signal)을 호출합니다
kernel code 커널 B의 PCB를 갱신해 시그널을 전달하고 A로 돌아갑니다
user code A A는 시스템 호출에서 돌아와 하던 일을 계속합니다
kernel code 커널 스케줄러가 B를 고르고, 시그널 마스크를 확인하고, 시그널 핸들러를 부릅니다
signal handler B B가 시그널을 처리(수신)하고 커널로 돌아갑니다
kernel code 커널 B의 레지스터를 복원하고 B로 돌아갑니다
user code B B가 끊겼던 지점부터 이어서 실행합니다
  • 핸들러는 B의 문맥에서, 사용자 모드로 실행됩니다. 연두 띠 안에서 핸들러를 실행하는 화살표는 점선 오른쪽, 즉 B의 영역에 있고, 띠 이름도 user code입니다. 커널은 핸들러를 직접 실행하지 않고, B가 사용자 모드로 돌아갈 때 B의 원래 코드 대신 핸들러로 가도록 길을 바꿔 줄 뿐입니다.
  • 핸들러가 끝나면 원래 코드로 바로 가지 않고 커널을 한 번 거칩니다. 리눅스에서는 핸들러가 반환하면 시그널 트램펄린(trampoline)을 거쳐 sigreturn 계열 시스템 호출(x86-64에서는 rt_sigreturn)이 불리도록 되어 있습니다. 시그널을 받기 직전에 보관해 둔 B의 레지스터를 커널이 복원해야 B가 끊긴 지점에서 아무 일 없었다는 듯 이어 갈 수 있기 때문입니다. 5.6절의 경쟁 조건 예제가 이 복원을 전제로 합니다.

다음 슬라이드는 같은 문맥 교환을 대기 중인 시그널이 없을 때와 있을 때로 나누어 비교합니다.

Important시그널은 ’사용자 모드로 돌아가는 길목’에서만 수신됩니다

커널은 시그널을 전달할 때 표시를 해 두고(받는 프로세스가 시스템 호출 안에서 잠들어 있으면 깨우기도 합니다), 그 프로세스를 커널 모드에서 사용자 모드로 돌려보낼 때마다 대기 중이면서 차단되지 않은 시그널이 있는지 확인합니다. 문맥 교환을 마치고 돌아갈 때가 대표적이고, 시스템 호출이나 인터럽트 처리를 마치고 돌아갈 때도 마찬가지입니다(3.7절 첫머리의 “프로세스로 돌아가기 전에”). 타이머 인터럽트는 어느 명령과 명령 사이에서든 걸릴 수 있으므로, 받는 프로세스 입장에서는 핸들러가 자기 코드의 어느 두 명령 사이에든 끼어들 수 있습니다. 5장의 문제들이 모두 여기서 나옵니다.

3.5 동시 흐름으로서의 시그널 핸들러 (Signal Handlers as Concurrent Flows)

시그널 핸들러는 메인 프로그램과 동시에(concurrently) 실행되는 별개의 논리적 흐름입니다. 프로세스가 아닙니다.

  • 13강 2.3절의 정의대로, 두 흐름의 실행 기간이 겹치면 동시적입니다. 핸들러는 메인 루프가 실행되는 기간 한가운데에 끼어들어 실행되므로 메인 루프와 동시적입니다.
  • 그러나 핸들러는 별도의 프로세스가 아니므로 주소 공간이 따로 없습니다. 메인 프로그램과 같은 전역 변수와 자료 구조를 공유하며, 이것이 5.6절 경쟁 조건의 뿌리입니다.

3.6 중첩된 시그널 핸들러 (Nested Signal Handlers)

핸들러도 다른 핸들러에 의해 끊길 수 있습니다.

단계 일어나는 일
(1) 메인 프로그램이 명령 \(I_{\text{curr}}\)를 실행하던 중 시그널 s를 잡습니다
(2) 제어가 핸들러 S로 넘어갑니다
(3) S가 실행되는 도중 시그널 t를 잡습니다
(4) 제어가 핸들러 T로 넘어갑니다
(5) T가 끝나 S로 돌아갑니다
(6) S가 끝나 메인 프로그램으로 돌아갑니다
(7) 메인 프로그램이 다음 명령 \(I_{\text{next}}\)부터 이어 실행합니다
  • 그림이 서로 다른 두 시그널 s와 t를 쓰는 데는 이유가 있습니다. 기본 설정에서는 핸들러가 실행되는 동안 그 핸들러의 시그널 자신이 차단되므로, 같은 시그널끼리는 중첩되지 않습니다. 같은 시그널끼리 중첩시키려면 4.9절의 SA_NODEFER 플래그가 필요합니다.

3.7 커널 내부: 구현 의사 코드 (Kernel Internals: Implementation Pseudo-Code)

지금까지의 동작을 커널이 어떻게 구현하는지 의사 코드로 보면 다음과 같습니다.

  • 프로세스마다 PCB에 비트 마스크 두 개를 둡니다 — 대기 중인 시그널 마스크(pending)와 차단된 시그널 마스크(blocked).
  • 프로세스로 돌아가기 전에, 대기 중이지만 차단되지 않은 시그널의 집합을 계산합니다.
  • 커널은 그 시그널들을 프로세스에 수신시킨 뒤에야 정상적으로 돌아갑니다.
int pending = 0;          // PCB 안: 대기 중인 시그널 (시그널 k = 비트 k)
int blocked = 0;          // PCB 안: 차단된 시그널

pnb = pending & ~blocked  // 대기 중이면서 차단되지 않은 시그널

while (pnb != 0) {
  Choose least nonzero bit k in pnb
  Force process p to receive signal k
    (receipt of the signal triggers some action by p)
  Clear bit k in pnb
}

Return to p
  • 전달 = pending의 비트 \(k\)를 켜는 것입니다. 교재(CS:APP 8.5.1절)의 설명대로, 커널은 시그널 \(k\)를 전달할 때 pending의 비트 \(k\)를 켜고 수신시킬 때 끕니다.
  • pnb = pending & ~blocked는 비트 연산 그대로입니다. ~blocked가 차단되지 않은 시그널의 집합이므로, 이것과 pending의 교집합이 “지금 수신시켜야 할 시그널”입니다.
  • 가장 낮은 비트부터 고르므로, 이 의사 코드에서는 번호가 작은 시그널부터 수신됩니다. 실제로는 POSIX가 여러 표준 시그널이 함께 대기할 때의 수신 순서를 정하지 않으며, 리눅스는 SIGSEGV 같은 동기 시그널을 먼저 고릅니다.
  • 의사 코드의 int 하나는 32비트이므로 1–31번 시그널이 비트 하나씩을 차지할 수 있습니다. 2.1절의 “대부분의 시스템에서 1–31번”과 맞아떨어집니다(리눅스 커널의 실제 시그널 집합은 64비트라 실시간 시그널까지 담습니다).

예를 들어 SIGINT(2번)와 SIGALRM(14번)이 대기 중인데 SIGINT가 차단되어 있다면 다음과 같습니다.

SIGALRM (비트 14) SIGINT (비트 2)
pending 1 1
blocked 0 1
pnb = pending & ~blocked 1 0

SIGALRM만 수신되고, SIGINT는 pending에 남아 차단이 풀릴 때를 기다립니다. 이 표현 방식에서 3.3절과 3.1절의 두 성질이 곧바로 나옵니다.

  • 큐에 쌓이지 않는다. 시그널마다 비트가 하나뿐이므로, 이미 1인 비트를 다시 켜는 두 번째 전달은 아무 흔적도 남기지 않습니다.
  • 차단해도 사라지지 않는다. 차단은 blocked의 비트일 뿐이고 pending의 비트는 그대로 남으므로, 차단을 푼 뒤 처음으로 프로세스로 돌아갈 때 수신됩니다(4.12절에서 확인합니다).

4.2 /bin/kill로 시그널 보내기 (Sending Signals with /bin/kill)

  • /bin/kill 프로그램은 임의의 시그널을 프로세스나 프로세스 그룹에 보냅니다.
    • 프로세스 그룹(process group)은 관련된 프로세스의 집합, 즉 pgrp ID가 같은 프로세스들입니다.
    • 예를 들어 셸에서 sort file1 | grep abc | more처럼 파이프라인을 실행하면 세 프로세스가 한 그룹이 됩니다.
  • 예
    • /bin/kill -9 21602 — 프로세스 21602에 SIGKILL(9번)을 보냅니다.
    • /bin/kill -9 -21602 — 프로세스 그룹 21602에 속한 모든 프로세스에 SIGKILL을 보냅니다. 슬라이드는 PID 앞의 -를 빨간색으로 강조합니다. 음수 PID는 프로세스 그룹을 뜻합니다.
  • 경로까지 적어 /bin/kill이라고 쓰는 것은, 셸(bash)에 같은 이름의 내장 명령 kill이 따로 있어서 외부 프로그램임을 분명히 하려는 것입니다.
$ ./pgrp 2
Parent: pid: 21602, pgid: 21602
 Child: pid: 21603, pgid: 21602
 Child: pid: 21604, pgid: 21602

$ ps -o pid,pgrp,comm
  PID  PGRP COMMAND
17740 17740 bash
21602 21602 pgrp
21603 21602 pgrp
21604 21602 pgrp
21962 21962 ps

$ /bin/kill -9 21602

$ ps -o pid,pgrp,comm
  PID  PGRP COMMAND
17740 17740 bash
21603 21602 pgrp
21604 21602 pgrp
22509 22509 ps

$ /bin/kill -9 -21602

$ ps -o pid,pgrp,comm
  PID  PGRP COMMAND
17740 17740 bash
22685 22685 ps

./pgrp 2는 자식 둘을 만들고 각자의 PID와 프로세스 그룹 ID(pgid)를 출력하는 프로그램입니다(코드는 슬라이드에 없습니다). ps -o pid,pgrp,comm은 PID, 프로세스 그룹, 명령 이름만 골라 보여 줍니다.

시점 그룹 21602에 남은 프로세스 설명
./pgrp 2 직후 21602(부모), 21603 · 21604(자식) 부모의 pgid가 자기 PID와 같으므로 부모가 그룹의 리더이고, 자식은 부모의 그룹을 물려받았습니다
/bin/kill -9 21602 뒤 21603, 21604 부모만 죽었습니다. 리더가 사라져도 그룹 ID 21602는 남은 자식들의 pgid로 그대로 남습니다
/bin/kill -9 -21602 뒤 없음 그룹에 속한 프로세스가 모두 죽었습니다
  • 부모가 먼저 죽은 두 자식은 13강 5.3절의 고아가 되지만, 그룹 소속은 바뀌지 않습니다. 그래서 그룹 단위의 kill로 한꺼번에 정리할 수 있습니다.
  • 매번 새로 실행되는 ps(21962 → 22509 → 22685)는 각자 자기 PID와 같은 그룹 ID를 가집니다. 셸이 명령을 실행할 때마다 새 프로세스 그룹을 만들기 때문이며, 다음 절의 주제입니다. bash(17740) 자신도 PID와 같은 그룹 ID를 가진 자기 그룹의 리더입니다.

4.3 프로세스 그룹 (Aside: Process Groups)

  • 모든 프로세스는 정확히 하나의 프로세스 그룹에 속합니다.
    • 자식 프로세스는 보통 부모와 같은 프로세스 그룹에 속합니다. fork가 그룹 ID를 물려주기 때문입니다.
    • 프로세스는 setpgid()를 불러 새 그룹을 만들 수 있습니다.
      • 같은 파이프라인에 속한 프로세스들은 같은 그룹 ID를 가집니다.
함수 하는 일
getpgrp() 현재 프로세스의 프로세스 그룹 ID를 돌려줍니다
setpgid() 프로세스의 프로세스 그룹을 바꿉니다(자세한 내용은 교재)
  • 그림의 작업(job)은 셸에 입력한 명령 줄 하나를 처리하려고 만든 프로세스들입니다. 작업 제어를 하는 대화형 셸은 작업마다 새 프로세스 그룹을 만들고, 보통 그 작업의 첫 프로세스의 PID를 그룹 ID로 씁니다. 앞 절의 pgrp가 자기 PID와 같은 pgid를 가진 이유입니다.
  • 교재(CS:APP 8.5.2절)에 따르면 setpgid(pid, pgid)에서 pid가 0이면 호출한 프로세스 자신을, pgid가 0이면 pid가 가리키는 프로세스의 PID를 그룹 ID로 씁니다. 따라서 setpgid(0, 0)은 자기 PID를 ID로 하는 새 그룹을 만들고 그 리더가 됩니다.
  • 포그라운드(foreground) 작업은 지금 터미널 입력을 받는 작업으로 한 번에 최대 하나이고, 백그라운드(background) 작업은 &를 붙여 실행한 작업처럼 터미널을 차지하지 않고 도는 작업으로 여러 개일 수 있습니다.

4.4 키보드로 시그널 보내기 (Sending Signals from the Keyboard)

Ctrl-C(Ctrl-Z)를 누르면 커널이 포그라운드 프로세스 그룹의 모든 프로세스에 SIGINT(SIGTSTP)를 보냅니다.

  • SIGINT — 기본 동작은 각 프로세스를 종료하는 것입니다.
  • SIGTSTP — 기본 동작은 각 프로세스를 정지(stop, suspend)하는 것입니다.
  • 슬라이드는 시그널을 받는 대상을 “포그라운드 프로세스 그룹의 모든 작업(every job)”이라고 적지만, 그림이 보여 주듯 실제로는 그 그룹에 속한 모든 프로세스가 시그널을 받습니다.
  • 시그널이 그룹 단위로 가기 때문에 sort file1 | grep abc | more를 실행하다 Ctrl-C를 누르면 세 프로세스가 함께 끝납니다. 반면 셸은 자기 그룹(10)에 있으므로 Ctrl-C에 죽지 않고 다음 명령을 기다립니다.
  • Ctrl-Z로 정지된 작업은 셸의 fg나 bg 명령으로 SIGCONT를 받아 다시 실행됩니다.

  • 반환값이 0보다 작으면 오류입니다. 자세한 내용은 man 페이지를 보라고 슬라이드는 덧붙입니다.
  • sig = 0은 “그 PID의 프로세스가 있고, 내가 시그널을 보낼 권한이 있는가”를 시그널 없이 확인하는 용도로 씁니다. 좀비도 있는 것으로 칩니다.
  • 4.2절의 /bin/kill -9 -21602는 kill(-21602, SIGKILL)과 같습니다.
  • pid의 네 경우는 13강 6.1절의 waitpid 인자 규칙(> 0, -1, 0, < -1)과 모양이 같습니다. 다만 -1이 waitpid에서는 “자식 중 아무나”이고 kill에서는 “권한이 있는 모든 프로세스”라는 점이 다릅니다.

4.6 kill() 예제: 자식 절반에게 SIGINT 보내기 (Sending Signals with the kill Function)

슬라이드의 killer.c는 자식 N개를 만든 뒤 그 절반에게 SIGINT를 보내고, 모두 수확하면서 각자 어떻게 끝났는지 출력합니다.

int main(int argc, char *argv[])
{
  pid_t pid[N];
  int i, child_status;

  for (i=0; i<N; i++) {
    if ((pid[i] = fork()) == 0) {              // child: sleep for certain amount of time
      sleep(i/2);
      return 100+i;                            // 종료 상태 = 100 + 자식 번호
    } else {                                   // parent: report
      printf("Created process %d\n", pid[i]);
    }
  }

  for (i=0; i<N; i+=2) {                       // parent: send SIGINT to half of children
    printf("Killing process %d\n", pid[i]);
    kill(pid[i], SIGINT);                      // 번호가 짝수인 자식(i = 0, 2, …)에게만 SIGINT
  }

  for (i=0; i<N; i++) {                        // parent: wait for children to terminate
    pid_t wpid = wait(&child_status);
    if (WIFEXITED(child_status)) {
      printf("Child %d terminated with exit status %d\n", wpid, WEXITSTATUS(child_status));
    } else {
      printf("Child %d terminated abnormally\n", wpid);
    }
  }
}

4.8 signal()로 등록하기 (Registering Signal Actions with signal())

signal()도 같은 일을 하는 더 간단한 함수입니다.

#include <signal.h>

typedef void (*sighandler_t)(int);

sighandler_t signal(int signum, sighandler_t handler);
  • signum — 대상 시그널입니다. SIGKILL과 SIGSTOP은 쓸 수 없습니다.
  • handler — 호출할 핸들러(시그널 잡기), 또는 SIG_IGN(무시), SIG_DFL(기본 동작)입니다.
  • 슬라이드는 반환형을 int로, 오류를 “0보다 작은 반환값”으로 적고 있습니다. 그러나 4.1절의 표와 man 페이지대로 반환형은 sighandler_t이며, 성공하면 이전 핸들러를, 실패하면 SIG_ERR를 돌려줍니다. 그래서 4.9절 이후의 예제 코드도 signal(...) == SIG_ERR로 오류를 검사합니다. 위 선언은 이에 맞춰 바로잡은 것입니다.
  • 슬라이드는 man 페이지의 경고도 옮겨 둡니다. signal()의 동작은 유닉스 버전마다 다르고 리눅스에서도 버전에 따라 달라져 왔으므로, 쓰지 말고 sigaction(2)을 쓰라는 것입니다.
Warningsignal()을 피해야 하는 이유

man 2 signal에 따르면 signal()로 등록한 핸들러의 의미는 두 갈래입니다.

System V 의미 BSD 의미
핸들러가 호출될 때 SIG_DFL로 되돌아감(진입하자마자 초기화되어 한 번만 잡힘) 등록이 유지됨
핸들러 실행 중 같은 시그널 차단되지 않음 차단됨
끊긴 시스템 호출 다시 시작하지 않음 일부 호출을 다시 시작함(SA_RESTART)

리눅스의 glibc는 기본적으로 BSD 의미를 주지만, 기능 검사 매크로(_DEFAULT_SOURCE 등)가 정의되지 않는 컴파일 환경(예: gcc -std=c11처럼 엄격한 표준 모드)에서는 System V 의미로 바뀝니다. 같은 코드가 환경에 따라 다르게 동작하는 셈입니다. sigaction은 이 세 가지를 sa_mask와 sa_flags로 명시하므로 이런 모호함이 없습니다. 이 강의의 예제들은 signal()과 sigaction()을 섞어 쓰는데, 출력은 리눅스의 기본 설정, 즉 BSD 의미를 기준으로 읽으면 됩니다.

4.9 등록 예제: 중첩되는 핸들러와 알람 (Registering Signal Actions)

슬라이드의 signal.c는 SIGINT와 SIGALRM에 핸들러를 등록한 뒤, 시그널이 올 때마다 처리하며 기다립니다.

void handler(int sig) {
  static int level = 0;                      // 중첩 깊이 (모든 호출이 공유)

  level++;
  printf("[nesting level %d] Hohoo, got signal %d\n", level, sig);
  sleep(3);
  level--;
}

void alarm_hdl(int sig) {
  printf("Wake up!\n");
  alarm(5);                                  // 다음 알람을 다시 예약
}

int main(int argc, char *argv[]) {
  struct sigaction action;

  action.sa_handler = handler;
  sigemptyset(&action.sa_mask);              // allow nested signals
  action.sa_flags = SA_RESTART | SA_NODEFER; // restart syscalls if possible

  if (sigaction(SIGINT, &action, NULL) < 0) {
    perror("Cannot install signal handler"); return EXIT_FAILURE;
  }

  if (signal(SIGALRM, alarm_hdl) == SIG_ERR) {
    perror("Cannot install signal handler"); return EXIT_FAILURE;
  }

  alarm(5);
  while (pause() == -1);                     // 시그널을 기다리는 무한 루프

  return EXIT_SUCCESS;
}

슬라이드는 SIGINT를 sigaction으로(파란색), SIGALRM을 signal로(빨간색) 등록해 두 방식을 대비합니다.

  • alarm(seconds)는 seconds초 뒤에 자기 자신에게 SIGALRM이 오도록 예약합니다. 이전 예약은 취소되고, 그 예약의 남은 초를 돌려줍니다. 알람은 한 번만 울리므로 alarm_hdl이 매번 alarm(5)로 다시 예약해 5초마다 Wake up!이 찍힙니다.
  • pause()는 시그널을 잡아 핸들러가 반환할 때까지 잠들며, 깨어나면 언제나 -1(errno는 EINTR)을 돌려줍니다. 따라서 while (pause() == -1);은 시그널을 처리하며 끝없이 기다리는 루프입니다.
  • sa_mask를 비운 것은 SIGINT 핸들러가 실행되는 동안 다른 시그널(예: SIGALRM)을 추가로 차단하지 않는다는 뜻입니다. 같은 SIGINT끼리의 중첩을 가능하게 하는 것은 4.7절의 SA_NODEFER입니다.

4.10 시그널 차단과 해제 (Blocking/Unblocking Signals)

#include <signal.h>

int sigprocmask(int how, const sigset_t *set,
                         sigset_t *oldset);
  • how — set을 어떻게 해석할지 정합니다.
how 의미 blocked의 변화
SIG_BLOCK set의 시그널을 차단합니다 \(\mathit{blocked} \leftarrow \mathit{blocked} \cup \mathit{set}\)
SIG_UNBLOCK set의 시그널의 차단을 풉니다 \(\mathit{blocked} \leftarrow \mathit{blocked} \setminus \mathit{set}\)
SIG_SETMASK 차단 마스크를 set으로 바꿉니다 \(\mathit{blocked} \leftarrow \mathit{set}\)
  • set — 차단하거나 풀 시그널의 집합입니다.
  • oldset — NULL이 아니면 이전 집합을 돌려받습니다. 이전 마스크를 받아 두었다가 SIG_SETMASK로 되돌리면, 원래 무엇이 차단되어 있었든 정확히 이전 상태로 돌아갈 수 있습니다.
  • 집합을 다룰 때는 sigsetops 함수들을 씁니다 — sigemptyset()(공집합), sigfillset()(모든 시그널), sigaddset()(하나 추가), sigdelset()(하나 제거).
  • 반환값이 0보다 작으면 오류입니다. 자세한 내용은 man 페이지에 있습니다.

sigprocmask가 바꾸는 것은 3.7절 의사 코드의 blocked 마스크입니다.

4.11 대기 중인 시그널 확인 (Checking for Pending Signals)

대기 중인 시그널 전체의 집합을 돌려받습니다.

#include <signal.h>

int sigpending(sigset_t *set);
  • set — 대기 중인(전달되었지만 수신되지 않은) 시그널의 집합이 담깁니다.
  • 어떤 시그널이 set에 들었는지는 sigsetops의 sigismember()로 확인합니다.
  • 반환값이 0보다 작으면 오류입니다. 자세한 내용은 man 페이지에 있습니다.

슬라이드는 이 함수가 대기 중인 시그널 전체를 돌려준다고 적지만, 더 정확히는 3.7절의 pending 마스크 가운데 blocked에도 들어 있는 부분, 즉 pending & blocked입니다. POSIX가 결과를 “호출한 스레드에 대해 차단되어 있으면서 대기 중인 시그널”로 정의하고, 리눅스 커널도 대기 집합을 blocked 마스크와 AND해서 돌려줍니다. 차단되지 않은 시그널은 어차피 다음 복귀 때 곧바로 수신되므로, 이 함수로 보이는 것은 언제나 차단된 시그널입니다. 4.1절 표가 이 함수를 “차단된 시그널의 상태 확인”이라고 부른 이유입니다.

4.12 차단 · 해제 · 상태 확인 예제 (Signals: Block, Unblock, & Check Status)

슬라이드의 block.c는 SIGINT를 차단했다가 푸는 동안 대기 중인 시그널을 1초마다 찍어, 차단 · 대기 · 수신을 눈으로 보여 줍니다.

void int_hdl(int sig) {  printf("Received SIGINT\n"); }

void alarm_hdl(int sig) {
  sigset_t set;
  char sigset[32];

  if (sigpending(&set) >= 0) {
    for (int i=1; i<32; i++) sigset[i] = (sigismember(&set, i)) > 0 ? 'P' : '.';
    sigset[0] = ' '; sigset[31] = '\0';
    printf("Pending signals: %s\n", sigset);
  }

  alarm(1);                                  // 1초마다 대기 중인 시그널을 출력
}

int main(int argc, char *argv[]) {
  sigset_t set;
  sigemptyset(&set);
  sigaddset(&set, SIGINT);                   // set = { SIGINT }

  if (signal(SIGALRM, alarm_hdl) == SIG_ERR) { perror("Cannot install signal handler"); return EXIT_FAILURE; }
  if (signal(SIGINT, int_hdl) == SIG_ERR)    { perror("Cannot install signal handler"); return EXIT_FAILURE; }

  alarm(1);

  struct timespec delay = { .tv_sec = 5, .tv_nsec = 0 };
  while ((nanosleep(&delay, &delay) < 0) && (errno == EINTR));   // 끊기면 남은 시간만큼 다시 잔다

  if (sigprocmask(SIG_BLOCK, &set, NULL) == 0) printf("SIGINT is now blocked.\n");

  delay.tv_sec = 5; delay.tv_nsec = 0;
  while ((nanosleep(&delay, &delay) < 0) && (errno == EINTR));

  if (sigprocmask(SIG_UNBLOCK, &set, NULL) == 0) printf("SIGINT is now unblocked.\n");

  delay.tv_sec = 5; delay.tv_nsec = 0;
  while ((nanosleep(&delay, &delay) < 0) && (errno == EINTR));

  return EXIT_SUCCESS;
}

main은 5초씩 세 번 잠듭니다 — SIGINT를 그대로 둔 5초, 차단한 5초, 다시 푼 5초. 그동안 alarm_hdl이 1초마다 sigpending으로 대기 중인 시그널을 찍습니다.

  • 출력 문자열의 \(i\)번째 글자가 시그널 \(i\)의 상태로, P는 대기 중, .은 아님을 뜻합니다. sigset[0]은 공백이고 sigset[31]은 문자열 끝 '\0'이므로, 화면에는 형식 문자열의 공백과 합쳐 공백 두 칸 뒤에 시그널 1–30번의 상태 30글자가 찍힙니다(31번은 보이지 않습니다).
  • nanosleep(&delay, &delay)는 시그널 핸들러에 끊기면 -1과 EINTR을 돌려주면서 남은 시간을 두 번째 인자에 적어 둡니다. 같은 변수를 두 인자로 넘겼으므로, 루프가 남은 시간만큼 다시 잠들어 1초마다 SIGALRM에 끊겨도 5초를 채웁니다. nanosleep은 SA_RESTART가 있어도 자동으로 다시 시작되지 않는 호출이라(man 7 signal) 이 루프가 필요합니다.

5.2 예제 1: 자식 수확 (Example 1: Reaping Children)

13강 5.4절에서 본 대로 셸이나 서버처럼 오래 사는 부모는 끝난 자식을 직접 수확해야 합니다. 그렇다고 wait에서 멈춰 기다리면 다른 일을 할 수 없습니다. 자식이 정지하거나 끝나면 커널이 부모에게 SIGCHLD를 보내므로(2.2절 표), SIGCHLD 핸들러에서 수확하면 부모는 자기 일을 하다가 자식이 끝날 때만 잠깐 수확하러 가면 됩니다. 첫 시도는 시그널 하나에 wait 하나입니다.

#define N 16
volatile int counter = 0;                    // 수확한 자식 수 (핸들러가 늘림)

void handler(int sig) {                                                  // signal handler
  int child_status;
  pid_t wpid = wait(&child_status);                                      // SIGCHLD 한 번에 수확 한 번
  if (WIFEXITED(child_status))
    printf("Child %d terminated with exit status %d\n", wpid, WEXITSTATUS(child_status));
  else
    printf("Child %d terminated abnormally\n", wpid);

  counter++;
}

int main(int argc, char *argv[]) {
  pid_t pid[N];
  if (signal(SIGCHLD, handler) == SIG_ERR) return EXIT_FAILURE;          // register signal handler

  printf("Creating %d children...\n", N);
  for (int i = 0; i < N; i++)
    if ((pid[i] = fork()) == 0) {                                        // child: sleep for some amount of time
      sleep(i/2);
      return 100+i;
    }

  for (int i = 0; i < N; i+=2) {                                         // parent: send SIGINT to half of children
    printf("Killing process %d\n", pid[i]);
    kill(pid[i], SIGINT);
  }

  printf("Waiting until all %d children have terminated...\n", N);       // parent: wait for termination
  while (counter < N) {
    sleep(1);
    printf("--> %d / %d terminated.\n", counter, N);
  }

  return EXIT_SUCCESS;
}

자식들의 동작은 4.6절의 killer.c와 같습니다(자식 \(i\)는 sleep(i/2) 뒤 100+i로 끝나고, 번호가 짝수인 자식은 SIGINT로 죽습니다). 다른 점은 부모가 wait 루프 대신 핸들러로 수확하고, counter가 \(N\)이 될 때까지 sleep(1)과 진행 상황 출력을 되풀이한다는 것입니다. sleep은 핸들러에 끊기면 남은 시간을 버리고 곧바로 돌아오므로, --> 줄은 대개 수확 직후에 찍히고 SIGCHLD가 없으면 1초마다 찍힙니다.

  • 두 번째 실행에서는 hel까지 입력하다 Ctrl-C를 눌렀습니다(키보드 인터럽트). 핸들러가 Received SIGINT를 찍은 뒤 read가 -1을 돌려주고, perror가 EINTR의 설명인 Interrupted system call을 붙여 출력한 뒤 프로그램이 끝납니다.
  • 세 번째 실행에서는 다른 터미널에서 killall -s SIGINT shell1로 SIGINT를 보냈습니다. 결과는 같지만, 마지막 줄에서 셸 프롬프트 뒤에 hel이 나타납니다. 키보드의 Ctrl-C(터미널의 INTR 문자)는 기본 설정(NOFLSH 꺼짐)에서 터미널의 입력 큐를 비우지만, 외부에서 kill로 보낸 시그널은 터미널을 거치지 않아 입력 큐를 비우지 않으므로, shell1이 읽지 못한 hel이 버퍼에 남아 있다가 다음에 터미널을 읽는 bash에게 넘어간 것입니다. (-s로 시그널을 지정하는 것은 리눅스(psmisc) killall의 문법입니다. macOS의 killall에서 -s는 시그널을 보내지 않고 대상만 보여 주는 옵션이므로 killall -INT shell1처럼 써야 합니다.)

해결책은 두 가지입니다.

  • 끊긴 시스템 호출을 확인하고, 필요하면 직접 다시 부르기
  • 시스템 호출을 자동으로 다시 시작하게 하기

해결책 1: 끊기면 다시 부르기 (shell2.c)

shell2.c는 read 한 줄만 다음 루프로 바꿉니다.

  while ((res = read(STDIN_FILENO, cmdline, sizeof(cmdline))) < 0) {
    if (errno != EINTR) break;               // EINTR이면 다시 read, 진짜 오류면 빠져나감
  }

  • 이제 SIGINT를 받아도 프로그램이 끝나지 않고, 핸들러가 Received SIGINT를 찍은 뒤 read가 다시 불려 입력을 계속 기다립니다. 사용자는 이어서 lo와 Enter를 입력했습니다.
  • Ctrl-C로 보낸 경우에는 Executing command: lo가 나옵니다. 슬라이드의 설명대로 Ctrl-C를 누르면 터미널이 그때까지 입력된 hel을 프로그램에 보내지 않고 버리기 때문입니다.
  • killall -s SIGINT shell2로 보낸 경우에는 hel이 버퍼에 그대로 남아 있으므로, 다시 부른 read가 hel과 lo를 이어 붙인 hello를 읽습니다.

해결책 2: 자동으로 다시 시작하기 (SA_RESTART)

해결책 2는 read를 원래의 한 줄로 두고, 핸들러를 등록할 때 SA_RESTART 플래그를 줍니다. 아래는 슬라이드의 코드에서 shell1.c와 달라진 줄만 추린 것으로, 같은 줄은 // … (shell1.c와 같음)으로 줄였습니다. 명령을 처리하는 if 블록도 조금 달라졌습니다.

  // …
  // … (shell1.c와 같음)
  action.sa_flags = SA_RESTART;              // 끊긴 시스템 호출을 커널이 다시 시작

  // … (shell1.c와 같음)
  char prompt[] = "> ";                      // 슬라이드에는 여는 따옴표가 둥근 따옴표(“)로 적혀 있음
  // … (shell1.c와 같음)

  res = read(STDIN_FILENO, cmdline, sizeof(cmdline));   // 재시도 루프가 필요 없다

  if (res >= 0) {
    cmdline[res-1] = '\0'; // remove '\n'
    if (strcmp(cmdline, "exit") == 0) break;
    printf("Executing command: '%s'...\n", cmdline);
  } else {
    perror("Error reading command");
  }
  // …

  • 슬라이드끼리 어긋나는 점. 이 코드의 상자에는 shell2.c라는 이름표가 붙어 있지만, 실행 화면의 프로그램은 ./shell3입니다. 또 코드의 형식 문자열대로라면 Executing command: 'hello'...가 찍혀야 하는데 화면에는 Executing command: hello가 찍혀 있고, break가 있다는 것은 바깥에 반복문이 있다는 뜻입니다. 이 코드는 명령을 반복해서 읽는 다른 판본에서 가져온 발췌로 보이므로, 해결책 2의 요점인 SA_RESTART 한 줄에 주목하면 됩니다. 슬라이드의 “> "는 둥근 따옴표 때문에 컴파일되지 않으므로 위 코드에서 바로잡았습니다.

5.5 경쟁 조건과 임계 구역 (Race Conditions and Critical Sections)

세 번째 문제를 다루기 전에 두 용어를 정의합니다.

Note정의 (Race Condition, Critical Section)
  • 경쟁 조건(race condition): 프로그램의 정확성이 프로그램이 통제할 수 없는 사건들의 순서나 타이밍에 결정적으로 좌우되는 결함입니다.
  • 임계 구역(critical section): 원자적으로(atomically), 즉 끊김 없이 한 번에 전부 실행되거나 아예 실행되지 않아야 하는 프로그램의 부분입니다.

시그널이 언제 수신될지는 3.4절대로 프로그램이 통제할 수 없으므로, 핸들러와 메인이 같은 자료를 건드리면 경쟁 조건이 생길 수 있습니다.

5.6 예제 3: 경쟁 조건 (Example 3: Race Condition)

int iBalance = 2000;
// …
static void addBonus(int iSig) {
    iBalance += 50;                          // 핸들러: 보너스 50 추가
}
int main(void) {
   signal(SIGINT, addBonus);                 // 슬라이드 공간을 아끼려고 오류 처리는 생략
   // …
   iBalance += 100;                          // 메인: 100 입금
   // …

전역 변수 iBalance는 잔액이고, SIGINT 핸들러 addBonus는 잔액에 50을, main은 100을 더합니다. 슬라이드는 지면을 아끼려고 이 예제부터 오류 처리를 생략한다고 밝힙니다. 위 코드는 슬라이드 46을 옮긴 것으로 addBonus가 static 함수이지만, 슬라이드 47–50(아래 그림 포함)은 같은 코드를 static 없이 적습니다. static은 함수 이름이 다른 파일에서 보이지 않게 할 뿐이므로 이 예제의 동작과는 상관없습니다. 어느 쪽이 먼저 실행되든 두 덧셈이 모두 반영되면 잔액은 \(2000 + 100 + 50 = 2150\)이어야 합니다.

문제는 C 문장 하나가 기계 명령 하나로 번역된다는 보장이 없다는 데 있습니다. 슬라이드처럼 컴파일러가 두 덧셈을 다음 어셈블리로 번역한다고 합시다(최적화 없이 컴파일하면 실제로 이와 같은 세 명령이 나옵니다).

iBalance += 100;   (main)        iBalance += 50;   (addBonus)
  movl iBalance, %eax              movl iBalance, %ecx    # 메모리 → 레지스터
  addl $100, %eax                  addl $50, %ecx         # 레지스터에서 더하기
  movl %eax, iBalance              movl %ecx, iBalance    # 레지스터 → 메모리

C 문장 하나가 읽기 → 더하기 → 쓰기의 세 명령이 되고, 3.4절대로 시그널은 그 어느 두 명령 사이에든 수신될 수 있습니다. 슬라이드는 최악의 경우를 세 단계로 따라갑니다.

단계 실행되는 명령 %eax (main) %ecx (핸들러) 메모리의 iBalance
(1) main()이 실행을 시작 movl iBalance, %eax 2000 2000
addl $100, %eax 2100 2000
(2) SIGINT 도착, 제어가 addBonus()로 movl iBalance, %ecx (2100 보관) 2000 2000
addl $50, %ecx (2100 보관) 2050 2000
movl %ecx, iBalance (2100 보관) 2050 2050
(3) addBonus()가 끝나고 제어가 main()으로 movl %eax, iBalance 2100 2100
    1. 동안 main의 %eax에 든 2100은 사라지지 않습니다. 3.4절대로 커널이 시그널을 수신시키기 전에 main의 레지스터를 보관했다가, 핸들러가 끝나면 그대로 복원하기 때문입니다. 핸들러가 %eax를 썼더라도 결과는 같습니다.
  • 바로 그 복원 때문에 (3)의 main은 핸들러가 끼어들기 전에 읽은 낡은 값으로 계산한 2100을 메모리에 씁니다. 최종 잔액은 2150이 아니라 2100이고, 50이 사라졌습니다.
  • 같은 프로그램이라도 핸들러가 main의 첫 movl보다 먼저 실행되거나(수신되거나) 마지막 movl이 끝난 뒤에 실행되면 잔액은 정상적으로 2150이 됩니다. 결과가 시그널이 수신되는 타이밍에 달려 있으므로, 5.5절의 정의 그대로 경쟁 조건입니다.

5.7 임계 구역 (Critical Sections)

해결책: 코드의 임계 구역(critical section)이 끊기지 않도록 해야 합니다.

  • 슬라이드는 addBonus의 iBalance += 50;과 main의 iBalance += 100;을 둘 다 임계 구역으로 표시합니다. 각 문장의 읽기-더하기-쓰기 세 명령은 다른 쪽이 중간에 끼어들지 못하게 한 덩어리로 실행되어야 합니다.
  • main 쪽은 5.9절의 지침대로 이 문장을 실행하는 동안 시그널을 차단하면 지킬 수 있습니다. 4.10절의 sigprocmask로 SIGINT를 차단한 뒤 덧셈을 하고 원래 마스크로 되돌리면, 그사이에 온 SIGINT는 3.1절대로 사라지지 않고 대기했다가 덧셈이 끝난 뒤 수신됩니다.
  • 핸들러 쪽은 main에게 끊길 일이 없습니다. 핸들러가 실행되는 동안 main은 멈춰 있기 때문입니다. 그러나 다른 핸들러나, 4.9절처럼 SA_NODEFER로 중첩을 허용한 같은 핸들러가 끼어들 수 있다면 핸들러 쪽도 같은 방식으로 보호해야 합니다.

  • 핸들러가 까다로운 이유는 메인 프로그램과 동시에 실행되면서 같은 전역 자료 구조를 공유하기 때문입니다.
    • 앞에서 본 대로 공유 자료 구조는 망가질 수 있습니다.
    • 동시성 문제는 학기 후반에 더 깊이 다룹니다.
  • 지금은 문제를 피하는 데 도움이 되는 지침을 따르기로 합니다.

5.9 안전한 핸들러 작성 지침 (Guidelines for Writing Safe Handlers)

슬라이드는 지침 여섯 가지를 두 장에 나누어 제시합니다.

지침 이유 · 방법
① 핸들러는 최대한 단순하게 예를 들어 전역 플래그만 세우고 반환한 뒤, 메인 프로그램이 그 플래그를 주기적으로 검사합니다
② 비동기 시그널 안전 함수만 호출 핸들러에서 안전하게 부를 수 있는 함수 목록은 man signal-safety에 있습니다. printf, sprintf, malloc, exit은 안전하지 않습니다
③ 진입할 때 errno를 저장하고 나갈 때 복원 핸들러가 메인 프로그램(이나 다른 핸들러)이 보고 있던 errno 값을 덮어쓰지 않게 합니다
④ 공유 자료 구조에 접근할 때는 모든 시그널을 잠시 차단 자료가 망가지는 것을 막습니다(5.7절)
⑤ 전역 변수는 volatile로 선언 컴파일러가 그 값을 레지스터에 담아 두고 재사용하지 못하게 합니다
⑥ 전역 플래그는 volatile sig_atomic_t로 선언 flag = 1이나 if (flag == 0) 같은 읽기 · 쓰기가 원자적으로 일어남을 보장합니다. 단 flag += 1이나 flag++는 원자적이라는 보장이 없습니다 
volatile int global;                         // ⑤ 전역 변수
volatile sig_atomic_t flag;                  // ⑥ 전역 플래그

각 지침을 이 강의의 예제와 이어 보면 다음과 같습니다.

  • ② 비동기 시그널 안전(async-signal-safe)은 핸들러에서 불러도 안전한 함수라는 뜻으로, 지역 변수만 쓰는 등 재진입 가능(reentrant)하거나 시그널에 끊길 수 없는 함수가 여기에 속합니다. printf나 malloc은 출력 버퍼나 힙 같은 전역 상태와 그것을 보호하는 잠금을 씁니다. 메인 프로그램이 printf 안에서 버퍼를 고치던 중에 핸들러가 다시 printf를 부르면 그 상태가 망가지거나, 잠금 때문에 프로그램이 멈출 수 있습니다. exit도 버퍼를 비우는 등의 정리 작업을 하므로 안전하지 않습니다. 반면 write, _exit, waitpid, kill, sigprocmask 등은 목록에 있습니다. 이 강의의 예제 핸들러들이 printf를 부르는 것은 출력을 보여 주기 위한 시연이며, 실제 코드에서 따라 할 것은 아닙니다.
  • ③ errno가 문제가 되는 것은 메인 프로그램이 실패한 시스템 호출 뒤에 errno를 확인하려는 순간, 그 사이에 핸들러가 실행되어 다른 시스템 호출로 errno를 바꿔 놓을 수 있기 때문입니다. 예를 들어 5.3절의 핸들러는 마지막 자식까지 수확하고 나면 waitpid가 -1을 돌려주면서 errno를 ECHILD로 바꿉니다.
  • ④는 5.7절에서 본 해결책 그대로입니다.
  • ⑤는 5.2–5.3절의 volatile int counter가 따른 지침입니다. while (counter < N) ;처럼 루프 안에 함수 호출이 없으면, 컴파일러는 루프 안에서 counter가 바뀔 수 없다고 보고 한 번 읽은 값을 레지스터에 담아 계속 재사용할 수 있습니다. 그러면 핸들러가 메모리의 값을 바꿔도 메인 루프는 그 변화를 끝내 보지 못합니다. 5.2절의 루프는 매번 sleep과 printf를 부르므로 실제 컴파일러는 호출할 때마다 counter를 메모리에서 다시 읽지만, 이는 우연에 기댄 것입니다. 핸들러와 공유하는 전역 변수는 지침대로 volatile로 선언해 두어야 합니다.
  • ⑥의 경고는 5.6절과 같은 이유입니다. flag++는 iBalance += 100;처럼 읽기 → 더하기 → 쓰기로 나뉠 수 있으므로, 그 사이에 핸들러가 끼어들 수 있습니다.

6. 예외적 제어 흐름의 비교 (Comparison of Exceptional Control Flow)

마지막으로 슬라이드는 14강의 저수준 ECF와 이번 강의의 고수준 ECF를 같은 항목으로 비교합니다.

항목 저수준 ECF: 예외 · 인터럽트 (Exceptions or Interrupts) 고수준 ECF: 시그널 (Signals)
출처 (sources) 명령의 실행 — 의도적인 것(소프트웨어 인터럽트)과 의도치 않은 것(명령 실행 중의 오류) / 외부 인터럽트(장치 인터럽트) 커널이 보내는 시그널 — 저수준 예외나 인터럽트의 결과(예: 타임아웃) / kill() 시스템 호출
전달 · 수신 (delivery) 현재 명령을 실행하는 도중이나 직후에 즉시 두 단계 — 커널에는 즉시(받는 프로세스의 PCB에 플래그 설정), 수신은 받는 프로세스가 다음에 스케줄될 때
처리 (handling) 프로세서가 — 전역 인터럽트 벡터 테이블 → 전역 커널 소프트웨어 핸들러 운영체제 커널이 — 프로세스별 시그널 핸들러
  • 슬라이드의 delivery는 이 포스트가 3.3절에서 나눈 전달과 수신을 함께 가리키므로, 표의 행 이름을 “전달 · 수신”으로 옮겼습니다.
  • 시그널이 닿는 방식(전달 · 수신)의 차이가 이 강의 전체를 요약합니다. 저수준 ECF는 하드웨어가 그 자리에서 커널로 제어를 넘기지만, 시그널은 전달 단계와 수신 단계가 나뉘어 있어(3.3–3.4절) 큐에 쌓이지 않고, 언제 끼어들지 모르며, 끊긴 시스템 호출과 경쟁 조건을 낳습니다(5장).
  • 처리 주체의 차이도 분명합니다. 인터럽트 벡터 테이블과 그 핸들러는 시스템 전체에 하나이고 커널 모드에서 실행되지만, 시그널 핸들러는 프로세스마다 따로 등록되며 그 프로세스의 사용자 코드로 실행됩니다(3.4절).
  • 3.2절의 SIGSEGV는 두 수준이 이어지는 예입니다. 잘못된 메모리 접근이 먼저 저수준 예외(#PF)로 즉시 커널로 넘어가고, 커널은 그 결과를 시그널로 바꾸어 전달하며, 프로세스는 사용자 모드로 돌아가기 직전에 그것을 수신합니다.

7. 요약 (Summary)

강의의 마지막 Module Summary 구분 슬라이드 뒤에 이어지는 요약은 다음과 같습니다.

  • 예외적 제어 흐름은 프로세서가 외부의 사건이나 예외적인 사건에 반응할 수 있게 합니다.
    • 명령의 실행이 실패하는 경우
    • 외부 장치가 사건을 알리는 경우(타이머, 네트워크 패킷 도착, 키보드 입력, …)
  • 고수준 메커니즘: 시그널
    • 어떤 사건이 일어났다는 알림입니다.
    • 커널이나 프로세스가 다른 프로세스에게 보냅니다.
    • 시그널은 잡거나(사용자가 지정한 핸들러 등록), 차단하거나, 무시하거나, 기본 동작으로 둘 수 있습니다.
  • 시그널의 전달과 수신은 동기적이지 않습니다.
    • 대기 중인 시그널은 프로세스로 돌아가기 직전에 수신됩니다.
  • 시그널 처리는 까다롭습니다.
    • 같은 프로그램 안에서 동시에 실행되는 흐름이 생깁니다.
    • 시그널 핸들러는 중첩될 수 있습니다.
    • 시그널은 큐에 쌓이지 않습니다.

단계 내용 근거
① 고수준 ECF 시그널은 사건의 종류(1–31번의 작은 정수)와 도착 사실만 사용자 프로세스에 알리는, 예외 · 인터럽트의 소프트웨어 판이다 Signals
② 기본 동작과 네 가지 반응 시그널마다 종료 · 무시 · 정지 · 계속 중 기본 동작이 있고, 프로세스는 잡기 · 차단 · 무시 · 기본 동작 중에서 고른다 — SIGKILL · SIGSTOP은 예외다 Signals, Signal Handling
③ 세 출처 커널 안의 사건(#PF → SIGSEGV), 프로그램의 kill 호출, 터미널(Ctrl-C · Ctrl-Z, /bin/kill)이 시그널을 만든다 Signal Sources, killer.c
④ 전달과 수신의 분리 전달은 받는 쪽 PCB의 상태를 바꾸는 일이고, 수신은 그 프로세스가 사용자 모드로 돌아가기 직전에 일어나므로 둘은 비동기다 — 핸들러는 어느 두 명령 사이에든 끼어들 수 있다 Signal Delivery and Reception
⑤ 비트 하나, 큐 없음 커널은 pending & ~blocked에 든 시그널을 수신시키며(의사 코드에서는 가장 낮은 비트부터), 종류마다 비트가 하나뿐이라 같은 시그널은 쌓이지 않고 차단한 시그널은 사라지지 않는다 Kernel Internals
⑥ 동시 흐름과 중첩 핸들러는 같은 프로세스 안에서 같은 전역 변수를 쓰는 별개의 논리적 흐름으로 메인과 동시적이며, 다른 핸들러에 다시 끊길 수 있다 Signal Handlers as Concurrent Flows, Nested Signal Handlers
⑦ 그룹 단위로 보내기 kill의 음수 PID와 키보드 시그널은 프로세스 그룹 단위로 가며, 셸은 작업마다 그룹을 만들어 Ctrl-C가 포그라운드 작업에만 닿게 한다 /bin/kill, Process Groups, Keyboard, Sending Signals
⑧ 등록 · 차단 · 확인 sigaction으로 핸들러 · 마스크 · 플래그를 정하고, sigprocmask로 차단하고, sigpending으로 대기 중인 시그널을 본다 — signal은 의미가 환경마다 달라 피한다 sigaction(), signal(), signal.c, block.c
⑨ 예제 1: 사라지는 SIGCHLD 시그널 하나에 wait 하나로는 합쳐진 SIGCHLD만큼 좀비가 남으므로, waitpid(-1, …, WNOHANG)을 반복해 쌓인 좀비를 모두 수확한다 countchildren1.c, countchildren2.c
⑩ 예제 2: 끊긴 시스템 호출 느린 시스템 호출은 핸들러 실행 뒤 EINTR로 실패하므로, 직접 다시 부르거나 SA_RESTART로 자동 재시작한다 shell1.c, shell2.c, shell3
⑪ 예제 3: 경쟁 조건 읽기 → 더하기 → 쓰기 사이에 핸들러가 끼어들면 갱신 하나가 사라지므로, 공유 자료를 고치는 임계 구역은 시그널을 차단해 끊기지 않게 지킨다 Race Condition, Critical Sections
⑫ 안전한 핸들러 단순하게, 비동기 시그널 안전 함수만, errno 보존, 공유 자료 접근 시 시그널 차단, volatile 전역 변수와 volatile sig_atomic_t 플래그 Guidelines for Writing Safe Handlers
⑬ 두 수준의 ECF 예외 · 인터럽트는 프로세서가 즉시 전역 핸들러로 처리하고, 시그널은 커널이 전달(PCB 표시)과 수신(복귀 직전)의 두 단계로 처리해 프로세스별 핸들러를 실행한다 Comparison of Exceptional Control Flow
